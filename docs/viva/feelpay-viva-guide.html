Project at a glance

Title: FeelPay: Payment as a Service Platform for India

Student: Chirag S Kotian, Reg. No. P05PP24S126026, MCA, Poornaprajna Institute of Management (PIM), Udupi

Internal guide: Prof. Venugopala Rao A S (Asst. Professor & HoD, MCA). External guide: Mr. Darshan, Manager, Feelitbuy Innovations.

One-line pitch: a self-hostable Indian payment gateway where merchants sign up, finish KYC, get test/live API keys, accept UPI, cards, netbanking and wallets, and receive settlements. Fees, 18% GST and 1% TDS (Sec. 194O) are computed inside the platform in paise.

Problem it solves

  • Commercial aggregators charge 2–3% plus GST, lock merchants in, and can freeze accounts.
  • Raw bank APIs (ISO 8583 / SOAP) have no dashboard, webhooks, vault or tooling.
  • Indian tax splits (18% GST on the fee, 1% TDS under Sec. 194O) are usually reconciled by hand from CSV exports.
  • Card-testing bots and noisy-neighbour load hurt small merchants.

How the key mechanisms work

Each item says what the code actually does, with the file to show the examiner.

Authentication

  • Dashboard login: POST /v1/merchants/login returns a 24-hour HS256 JWT (expires_in: 86400) with role, e.g. merchant_owner.
  • Passwords are hashed with Argon2id (src/api/auth.rs). The admin API also accepts legacy bcrypt hashes.
  • API keys (fp_test_… / fp_live_…) are stored as a SHA-256 hash plus a masked copy; lookup compares hashes (src/middleware/auth.rs:56).
  • JWT validation pins Algorithm::HS256 to block algorithm-confusion attacks.

Idempotency

Mutating calls accept an Idempotency-Key header. check_idempotency and store_idempotency_response in src/api/payments.rs return the stored response for a repeated key, so a client retry after a timeout never charges twice.

Money in paise

All amounts are i64 paise (₹10 = 1000). Fee math in src/engine/fees.rs uses rust_decimal for the percentage and GST step, then rounds back to i64. Floats are never used for money.

fee = amount × percentage / 100 + flat_fee   (clamped to min/max)
GST exclusive: gst = fee × 0.18
GST inclusive: base = fee / 1.18, gst = fee − base
net = amount − fee − gst

TDS (1%, Sec. 194O) is calculated in src/engine/services/settlement_advanced.rs at settlement time.

Double-entry ledger

src/engine/services/ledger.rs keeps ledger_accounts (merchant, platform, escrow…) and ledger_entries. Each transaction posts balanced debit and credit rows inside one DB transaction, so the sum of debits always equals the sum of credits.

Card vault

src/engine/vault.rs encrypts card data with AES-256-GCM using a 32-byte key from VAULT_ENCRYPTION_KEY (64 hex chars) and a random nonce per record. The app keeps only a token. GCM's auth tag detects tampering.

Smart routing

src/engine/routing.rs ranks connectors: healthy first, then higher success rate (basis points), then lower priority number, then lower cost. Registered processors at startup: simulator, card, upi, netbanking, wallet.

Webhooks

Events are signed with HMAC-SHA256 and sent with X-FeelPay-Signature and X-FeelPay-Event. Failed deliveries retry with exponential backoff: 1 min, 5 min, 15 min, 1 h, 6 h, 24 h, and stop after 7 attempts (src/engine/services/webhook.rs:158).

Fraud and abuse defences

  • Replay prevention: request timestamp must be within 300 seconds; each nonce is stored in Redis for 300 s and rejected if seen again.
  • Velocity checks: per-minute limits on the same card, same IP and same device fingerprint.
  • Blacklist service, risk engine, IP allow-list, maintenance mode, per-request IDs.
  • In test mode the gateway starts without Redis ("Redis unavailable; continuing startup in test mode"), so these Redis checks are inactive locally.

Multi-tenant isolation

Shared tables with a merchant_id column. Every handler takes merchant_id from the verified JWT or API key and filters queries with it. Postgres RLS policies exist (migrations/20240110000002_rls_policies.sql, using app.current_tenant_id) as a second layer.

KYC onboarding

Wizard validates PAN ([A-Z]{5}[0-9]{4}[A-Z]), 15-char GSTIN and 11-char IFSC, uploads documents, and waits for admin approval in the KYC queue. Live mode stays locked until approval. Dashboard shows "Your KYC status is pending" until then.

Run it for the demo

All four services, one command

./run.sh all --test --dev -y

Starts Gateway :8080, Admin API :8081, Dashboard :3000, Admin UI :3001. Health URLs: http://127.0.0.1:8080/v1/health and http://127.0.0.1:8081/health. Stop with Ctrl+C, or ./run.sh clean.

Important: point the UIs at your local backends

The dev .env files in dashboard/ and admin/ point to the Render deployment, so a plain ./run.sh makes the local UIs call the cloud APIs. The admin login then spins forever if Render is asleep. For a local demo, start the two UIs with overrides:

cd dashboard && VITE_API_BASE_URL=http://127.0.0.1:8080 VITE_SANDBOX_API_BASE_URL=http://127.0.0.1:8080 VITE_LIVE_API_BASE_URL=http://127.0.0.1:8080 pnpm dev --port 3000
cd admin && VITE_ADMIN_API_BASE_URL=http://127.0.0.1:8081 pnpm dev --port 3001

Logins

  • The admin login form is pre-filled with admin@feelpay.local, which does not exist in the database. Clear it.
  • Seeded accounts with admin rights: test@feelpay.com, test@merchant.com, merchant@example.com, testmerchant@example.com. Their password is written in the comment on line 1 of migrations/20260515000012_reset_test_merchant_password.sql.

Code review findings

Ponytail review (YAGNI, root-cause, minimal diff) of the last code commit plus defects found during the live run. Most severe first.

fixed
Unauthenticated admin token endpoint

GET /admin/bootstrap-token (and /api/admin/bootstrap-token) returned a valid admin JWT to anyone. Nothing in the UI used it. The route, handler, auth-bypass and docs entry are removed; both paths now return 401. Redeploy Render to close it there too.

admin/server/src/main.rs · middleware.rs · docs.rs
fixed
Capture and refund failed: ledger system accounts missing, refunds posted negative amounts

record_transaction needs a platform and an escrow account; no migration created them. New migration 20261029000000_seed_ledger_system_accounts.sql inserts them if missing. Refunds then hit CHECK (amount > 0) because they passed -amount; the ledger now posts reversals as positive amounts in the opposite direction (debit merchant, credit escrow).

src/engine/services/ledger.rs · migrations/20261029000000_seed_ledger_system_accounts.sql
risk
Capture uses a hard-coded 3% fee

capture_payment computes amount × 3 / 100 and ignores the configurable fee engine in fees.rs (fee plans, caps, GST). Ledger fees can disagree with displayed pricing.

src/api/payments.rs:800
risk
Batch refund swallows errors

Both the status update and the ledger post end in .ok(), so a failed ledger write still counts as a successful refund.

src/api/payments.rs:1273, 1287
yagni
3DS2 service is not wired

ThreeDsService is never referenced outside its own file. After the last commit, verify_cres always marks the challenge failed. Either wire it into the card flow or describe 3DS as planned work.

src/engine/services/three_ds.rs
risk
RLS policies are not activated by the app

Policies read app.current_tenant_id, but no Rust code sets it, and the Neon owner role bypasses RLS without FORCE ROW LEVEL SECURITY. Real isolation today is the merchant_id filter in each query.

config
Local dev UIs call the cloud

dashboard/.env and the admin fallback in admin/src/hooks/useApi.ts:1 point to Render. .env.production already covers deploys, so dev .env should use localhost.

config
Admin login pre-filled with a non-existent user and a password in source

admin/src/App.tsx:318 hard-codes default email and password state. Remove before submission.

nit
Last commit: unneeded edits
  • return matches!(…); in is_safe_method is non-idiomatic Rust; the original expression was correct. Revert.
  • Validation::new(HS256) is the same as Validation::default(); harmless, it documents intent.
  • ~3,800 lines of graphify-out churn rode along in a security fix commit; keep generated files in their own commit.
nit
Bad-request bodies leak serde text and skip the JSON envelope

Malformed payment JSON returns plain text like Json deserialize error: unknown variant… instead of the usual {success,data,error} envelope.
