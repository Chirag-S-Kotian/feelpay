Payment lifecycle in plain words

  1. Order: customer clicks Pay on the merchant's site. The merchant's server asks FeelPay to create a payment for, say, ₹1,200 (120000 paise).
  2. Authenticate: FeelPay checks the API key or login token and the merchant's role.
  3. Protect: idempotency key stops double charges; velocity and risk rules stop bots.
  4. Route: the engine picks the healthiest, most successful connector for that method.
  5. Authorise / capture: UPI is captured at once; cards are authorised first and captured later.
  6. Ledger: on capture, escrow is debited 120000, merchant credited 116400 and platform credited 3600 (3% fee), all in one DB transaction.
  7. Notify: a webhook with X-FeelPay-Signature tells the merchant's server the result; retries if their server is down.
  8. Refund / dispute: refunds post the reverse entries; disputes track evidence and deadlines.
  9. Settle: the merchant's balance, minus fees, GST and 0.1% TDS, is paid to their bank account.

How the key mechanisms work

Each item says what the code actually does, with the file to show the examiner.

Authentication

  • Dashboard login: POST /v1/merchants/login returns a 24-hour HS256 JWT (expires_in: 86400) with role, e.g. merchant_owner.
  • Passwords are hashed with Argon2id (src/api/auth.rs). The admin API also accepts legacy bcrypt hashes.
  • API keys (fp_test_… / fp_live_…) are stored as a SHA-256 hash plus a masked copy; lookup compares hashes (src/middleware/auth.rs:56).
  • JWT validation pins Algorithm::HS256 to block algorithm-confusion attacks.

Idempotency

Mutating calls accept an Idempotency-Key header. check_idempotency and store_idempotency_response in src/api/payments.rs return the stored response for a repeated key, so a client retry after a timeout never charges twice.

Money in paise

All amounts are i64 paise (₹10 = 1000). Fee math in src/engine/fees.rs uses rust_decimal for the percentage and GST step, then rounds back to i64. Floats are never used for money.

fee = amount × percentage / 100 + flat_fee   (clamped to min/max)
GST exclusive: gst = fee × 0.18
GST inclusive: base = fee / 1.18, gst = fee − base
net = amount − fee − gst

TDS (0.1% from 1 Oct 2024, earlier 1%; Sec. 194O) is calculated in src/engine/services/settlement_advanced.rs at settlement time.

Double-entry ledger

src/engine/services/ledger.rs keeps ledger_accounts (merchant, platform, escrow…) and ledger_entries. Each transaction posts balanced debit and credit rows inside one DB transaction, so the sum of debits always equals the sum of credits.

Card vault

src/engine/vault.rs encrypts card data with AES-256-GCM using a 32-byte key from VAULT_ENCRYPTION_KEY (64 hex chars) and a random nonce per record. The app keeps only a token. GCM's auth tag detects tampering.

Smart routing

src/engine/routing.rs ranks connectors: healthy first, then higher success rate (basis points), then lower priority number, then lower cost. Registered processors at startup: simulator, card, upi, netbanking, wallet.

Webhooks

Events are signed with HMAC-SHA256 and sent with X-FeelPay-Signature and X-FeelPay-Event. Failed deliveries retry with exponential backoff: 1 min, 5 min, 15 min, 1 h, 6 h, 24 h, and stop after 7 attempts (src/engine/services/webhook.rs:158).

Fraud and abuse defences

  • Replay prevention: request timestamp must be within 300 seconds; each nonce is stored in Redis for 300 s and rejected if seen again.
  • Velocity checks: per-minute limits on the same card, same IP and same device fingerprint.
  • Blacklist service, risk engine, IP allow-list, maintenance mode, per-request IDs.
  • In test mode the gateway starts without Redis ("Redis unavailable; continuing startup in test mode"), so these Redis checks are inactive locally.

Multi-tenant isolation

Shared tables with a merchant_id column. Every handler takes merchant_id from the verified JWT or API key and filters queries with it. Postgres RLS policies exist (migrations/20240110000002_rls_policies.sql, using app.current_tenant_id) as a second layer.

KYC onboarding

Wizard validates PAN ([A-Z]{5}[0-9]{4}[A-Z]), 15-char GSTIN and 11-char IFSC, uploads documents, and waits for admin approval in the KYC queue. Live mode stays locked until approval. Dashboard shows "Your KYC status is pending" until then.

RBI rules and legal framework for an Indian payment gateway

Summary of the rules a real operator must follow, with official references. This is a study summary, not legal advice; quote the circular numbers and check the RBI text before relying on exact figures.

1. Payment and Settlement Systems Act, 2007 (the parent law)

  • Section 4: nobody except RBI may start or operate a payment system without RBI authorisation.
  • Section 7: RBI issues or refuses that authorisation.
  • Section 18 read with 10(2): lets RBI issue directions; the 2025 PA Directions are issued under these sections (plus FEMA 10(4) and 11(1) for cross-border).
  • Section 26: offences and penalties, including running a payment system without authorisation.

Payment gateway vs aggregator: a Payment Gateway (PG) only provides the technology and never handles funds, so it needs no RBI licence. A Payment Aggregator (PA) collects customer money and settles it to merchants, so it must be RBI-authorised. FeelPay's design (escrow ledger, settlements) is a PA.

2. RBI (Regulation of Payment Aggregators) Directions, 2025

Issued 15 September 2025, ref. RBI/DPSS/2025-26/141, CO.DPSS.POLC.No.S-633/02-14-008/2025-26. It consolidates and replaces the 17 March 2020 PA-PG Guidelines (DPSS.CO.PD.No.1810/02.14.008/2019-20), the 31 March 2021 clarification and the 31 October 2023 PA-Cross Border circular.

4. Data protection and IT law

  • Digital Personal Data Protection Act, 2023: consent, purpose limitation, security safeguards, breach reporting, right to erasure. DPDP Rules, 2025 notified 13–14 Nov 2025; most obligations apply about 18 months later (around May 2027).
  • IT Act, 2000, Section 43A and the SPDI Rules, 2011 (reasonable security for sensitive data, including financial data) remain in force during the DPDP transition.
  • PCI DSS v4.0 (PCI Security Standards Council, March 2022; v4.0.1 June 2024): rules for storing and transmitting card data.

5. Tax rules

  • GST 18% applies to the gateway's fee (MDR), not to the sale amount. Merchants can usually claim it as input tax credit with a GST invoice. Example: 2% fee → 2.36% effective.
  • Zero MDR: by government mandate from 1 Jan 2020, merchants are not charged MDR on RuPay debit cards and BHIM-UPI.
  • Section 194O TDS: e-commerce operators deduct TDS on the gross sale value paid to sellers. Introduced at 1% from 1 Oct 2020; cut to 0.1% from 1 Oct 2024 by the Finance (No. 2) Act, 2024. Without PAN the rate is 5% (Section 206AA). FeelPay's code was updated to 0.1% on 29 Oct 2026.

6. UPI background

NPCI was set up in 2008 as a not-for-profit company by RBI and the Indian Banks' Association. UPI was piloted on 11 April 2016 by RBI Governor Dr. Raghuram Rajan in Mumbai with 21 banks, and went public on 25 August 2016. A payer uses a VPA (e.g. name@bank); NPCI's switch routes the request between the payer's and payee's banks.

Checklist: building a compliant payment gateway in India

  1. Decide the role: PG (technology only, no licence) or PA (handles funds, RBI authorisation).
  2. For a PA: incorporate a company, reach ₹15 crore net worth, apply to RBI with board-approved policies.
  3. Open an escrow account with a scheduled commercial bank; settle merchants only from it.
  4. Onboard merchants with KYC per the RBI KYC Master Direction; register with FIU-IND.
  5. Never store raw card data; use card network tokenisation; get PCI-DSS certified.
  6. Host all payment data in India; get yearly CERT-In-empanelled audits and twice-yearly VAPT.
  7. Follow e-mandate rules for subscriptions; follow DPDP for personal data.
  8. Apply GST on fees and Section 194O TDS; publish grievance officer, terms and privacy policy.
  9. Integrate NPCI (UPI) and card networks through a sponsor/acquiring bank.

Design decisions

  • Shared tables + merchant_id instead of a database per merchant: cheap, one migration path, global analytics. Every handler filters by the merchant id taken from the verified token.
  • BIGINT paise: exact integer money; ₹1,200.50 = 120050.
  • Transactions: ledger postings run in one DB transaction, so debits and credits are never half-written. Live proof: for a captured and fully refunded payment, debits minus credits = 0.
  • Constraints: foreign keys to merchants, CHECK (amount > 0), unique indexes (e.g. one ledger account per owner and type).
  • RLS: policies on 10 tables use current_setting('app.current_tenant_id'); the app does not yet set it per request, so app-layer filtering is the active control.

Code review findings

Ponytail review (YAGNI, root-cause, minimal diff) of the last code commit plus defects found during the live run. Most severe first.

fixed
Unauthenticated admin token endpoint

GET /admin/bootstrap-token (and /api/admin/bootstrap-token) returned a valid admin JWT to anyone. Nothing in the UI used it. The route, handler, auth-bypass and docs entry are removed; both paths now return 401. Redeploy Render to close it there too.

admin/server/src/main.rs · middleware.rs · docs.rs
fixed
Capture and refund failed: ledger system accounts missing, refunds posted negative amounts

record_transaction needs a platform and an escrow account; no migration created them. New migration 20261029000000_seed_ledger_system_accounts.sql inserts them if missing. Refunds then hit CHECK (amount > 0) because they passed -amount; the ledger now posts reversals as positive amounts in the opposite direction (debit merchant, credit escrow).

src/engine/services/ledger.rs · migrations/20261029000000_seed_ledger_system_accounts.sql
risk
Capture uses a hard-coded 3% fee

capture_payment computes amount × 3 / 100 and ignores the configurable fee engine in fees.rs (fee plans, caps, GST). Ledger fees can disagree with displayed pricing.

src/api/payments.rs:800
risk
Batch refund swallows errors

Both the status update and the ledger post end in .ok(), so a failed ledger write still counts as a successful refund.

src/api/payments.rs:1273, 1287
yagni
3DS2 service is not wired

ThreeDsService is never referenced outside its own file. After the last commit, verify_cres always marks the challenge failed. Either wire it into the card flow or describe 3DS as planned work.

src/engine/services/three_ds.rs
risk
RLS policies are not activated by the app

Policies read app.current_tenant_id, but no Rust code sets it, and the Neon owner role bypasses RLS without FORCE ROW LEVEL SECURITY. Real isolation today is the merchant_id filter in each query.

fixed
TDS rate out of date

calculate_tds used 1%. Section 194O has been 0.1% since 1 Oct 2024; code and test now use 0.1%.

src/engine/services/settlement_advanced.rs
fixed
Local dev UIs called the cloud; admin login pre-filled

run.sh now points both UIs at the local backends. The admin login no longer ships a default email and password in source.

run.sh · admin/src/App.tsx
risk
Database region is outside India

The Neon host is in ap-southeast-1 (Singapore). RBI's 2018 data-localisation circular requires payment data to be stored only in India. Fine for a test project; a real launch must use an Indian region.

nit
Last commit: unneeded edits
  • return matches!(…); in is_safe_method is non-idiomatic Rust; the original expression was correct. Revert.
  • Validation::new(HS256) is the same as Validation::default(); harmless, it documents intent.
  • ~3,800 lines of graphify-out churn rode along in a security fix commit; keep generated files in their own commit.
nit
Bad-request bodies leak serde text and skip the JSON envelope

Malformed payment JSON returns plain text like Json deserialize error: unknown variant… instead of the usual {success,data,error} envelope.
