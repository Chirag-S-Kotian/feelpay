1. Abstract
FeelPay is a state-of-the-art, high-performance, compliance-ready, multi-tenant Indian payment gateway and payment aggregator platform. The platform is specifically engineered to provide secure, low-latency, and sovereign digital transaction processing for online merchants. Unlike standard client-side wrappers or simple payment integrations that rely heavily on third-party aggregators, FeelPay implements an end-to-end proprietary transaction and routing engine, giving merchants absolute sovereignty over their financial routing, platform fees, and domestic ledger accounts. The architecture is split into a highly responsive merchant dashboard built using React 19, TypeScript, and Vite, and a concurrent, type-safe backend API service compiled in Rust using the Actix Web framework and SQLX. Data persistence is managed via an optimized cloud PostgreSQL (Neon) database deployed in the Mumbai (ap-south-1) region, guaranteeing sub-10ms query latencies for local domestic traffic, while caching, real-time rate limiting, and velocity analytics are powered by Redis.
The core value proposition of FeelPay lies in its native compliance and automated accounting of Indian-specific financial mandates. The system incorporates a highly accurate double-entry financial ledger that processes all monetary transaction values in integer paise minor units, eliminating the floating-point rounding hazards typical of standard processors. On transaction success, the engine atomically calculates platform transactional fees (percentage or flat), deducts 18% Goods and Services Tax (GST) on platform charges, and tracks 1% Tax Deducted at Source (TDS) under Section 194O of the Indian Income Tax Act during T+0 (instant UPI payouts) or standard T+2 settlement payouts. Merchant verification is handled via an automated, multi-state KYB/KYC onboarding pipeline collecting PAN, GSTIN, and IFSC data, complete with a secure PDF document vault. Security is enforced through Redis sliding-window velocity checks, dynamic IP/domain/BIN blacklists, SHA-256 browser device fingerprinters, and a robust replay-attack defense utilizing temporal cryptographic nonces. Furthermore, an offline tokio-driven worker handles async PDF/CSV tax reporting and signed webhooks (HMAC-SHA256) with exponential backoff schedules.

2. Motivation to Choose This Work
The rapid digitization of the Indian financial ecosystem—accelerated by the Unified Payments Interface (UPI), mobile banking, and comprehensive government initiatives like the Digital India campaign—has fundamentally transformed domestic online commerce. Today, online enterprises of all scales, from local e-commerce startups to massive SaaS platforms, rely heavily on digital payment gateways. However, the domestic payment aggregator market is currently dominated by a narrow set of closed-source proprietary players (e.g., Razorpay, Cashfree, PayU, PhonePe PG). This high centralization introduces substantial challenges, including steep transaction commission fees (2% to 3% flat), lack of transparency in settlement schedules, arbitrary account suspensions, and complex compliance hurdles under the Reserve Bank of India (RBI) payment aggregator guidelines.
Integrating standard gateways often exposes applications to vendor lock-in, restricting custom business rules, direct merchant-bank integrations, and multi-tenant reseller distributions. There is a glaring academic and industrial need for an open-architecture, self-hosted payment gateway engine that handles security, double-entry financial accounting, and local regulatory compliance. Designing and implementing FeelPay from the ground up offers an outstanding opportunity to build a clean-room, production-grade financial platform that models real-world bank integrations, providing deep technical insights into concurrent system engineering.
From a software engineering perspective, payment processing requires absolute transactional reliability, low latency, and memory safety. Traditional scripting runtimes (such as Node.js or Python) struggle to deliver the combined requirements of concurrency safety and data-race protection under sudden transaction surges, frequently suffering from CPU blocks during cryptographic tasks. Choosing the combination of Rust and React 19 is motivated by exploring the cutting edge of safe software engineering. Rust's strict compiler guarantees, compile-time thread safety, and memory safety without a garbage collector make it the premier language for building secure financial backends, while React 19 provides state reliability on the client application.
Finally, the project directly addresses the complex operational compliance guidelines enforced in India. Incorporating realistic workflows like the Digital Personal Data Protection (DPDP) Act 2023 for customer data vaulting, automating TDS (Tax Deducted at Source) deductions for instant payouts under Section 194O, calculating platform fees with GST, and supporting UPI Deep Linking provides profound exposure to fintech systems design. FeelPay bridges the gap between academic software concepts and high-performance financial systems engineering.

3. Literature Review
3.1 High Concurrency Runtimes and Asynchronous Systems Programming
In the design of modern financial APIs, the choice of architectural runtime determines transaction throughput, latency, and operational cost. Historically, legacy platforms utilized synchronous multi-threaded architectures (e.g., traditional Java enterprise applications). In a synchronous architecture, each incoming transactional request is assigned to a dedicated operating system thread. While simple to implement, this model scales poorly because OS thread context-switching consumes substantial memory (typically 1MB to 10MB per thread) and CPU cycles. Under transaction surges, traditional servers exhaust available system resources and experience extreme latency degradation or crash due to Out-Of-Memory (OOM) faults.
To mitigate this, single-threaded asynchronous loops (like Node.js) grew in popularity. While Node.js multiplexes connections efficiently via an event loop, it is severely limited by CPU-bound workloads. Payment gateways are inherently compute-intensive: they perform dynamic HMAC-SHA256 webhook signing, asymmetric AES-256 encryption, device fingerprint parsing, and complex ledger tax calculations. Because Node.js runs on a single execution thread, any prolonged CPU-intensive cryptographic task blocks the event loop, causing all concurrent network connections to queue up and latency to spike.
Recent research by Vardanega et al. (2021) evaluates concurrent systems programming languages for financial infrastructures. Their findings show that compile-time safe, non-garbage-collected languages like Rust outperform both Java and Node.js by significant margins. Rust's premier web frameworks—specifically Actix Web, built on top of the Tokio asynchronous execution runtime—utilize light green-threads known as tasks. These tasks are multiplexed over a tiny pool of operating system threads. By avoiding virtual machine overhead and execution garbage collection, Rust achieves sub-millisecond route handling and minimizes memory consumption to a fraction of traditional servers, guaranteeing peak TPS scaling.

3.2 Cryptographic Card Vaulting and PCI-DSS Compliance Boundaries
Handling customer debit and credit card numbers introduces high security liabilities. Any system that stores, transmits, or processes Primary Account Numbers (PANs) is legally subject to the Payment Card Industry Data Security Standard (PCI-DSS) auditing guidelines. Traditional database structures stored card numbers in plain text or simple database tables, exposing sensitive details to SQL injection compromise, logical leakage, or internal access abuse. PCI-DSS enforces strict tokenization rules where raw card numbers must be stripped from the core application database and stored in an isolated, heavily audited server environment known as a vault.
Studies by Menzies and Hu (2022) on cryptographic data architectures demonstrate that tokenization vaults must enforce strict separation of concerns. The vault operates as a self-contained service with separate databases and dedicated encryption hardware or software keys. When card credentials enter the system, they are directly routed to the cryptographic vault. The vault encrypts the PAN using symmetric authenticated encryption—specifically Advanced Encryption Standard in Galois/Counter Mode (AES-256-GCM). AES-256-GCM is preferred because it guarantees both data confidentiality and authenticity: any attempt to alter the ciphertext without the secret key is automatically detected during decryption, preventing database injection manipulation.
The encrypted card data is mapped to a unique, randomly generated token and a secure non-reversible card fingerprint hash. The core transaction engine receives only this token and fingerprint for transaction execution, ensuring that the primary database and application logs remain completely free of raw card data. This design minimizes the merchant's PCI-DSS audit scope from complex network-wide audits to simple self-assessment checks. In FeelPay, this architectural design is implemented in `src/vault/` and `src/engine/vault.rs`, which hashes card strings and encrypts card payloads with dynamic salts before writing to PostgreSQL, guaranteeing full alignment with modern bank-grade vaulting methodologies.

3.3 Multi-Tenant Database Isolation and Zero-Trust Middleware Security
Software-as-a-Service (SaaS) financial applications serving multiple independent merchants must enforce complete data isolation. Cabral et al. (2023) evaluate multi-tenancy models in high-load database systems, outlining three primary approaches. The first is *Database-per-tenant*, which provides the highest security but is extremely expensive and complex to migrate at scale. The second is *Schema-per-tenant*, which keeps schemas isolated on a single database but makes cross-tenant analytical reporting highly difficult. The third is *Shared-table logical isolation*, where all tenants write to the same table partitions, scoped by a unique tenant identifier. While highly resource-efficient and easy to scale, shared-table models are vulnerable to data leakage if a developer misses a tenant filter query.
To mitigate this structural risk, modern relational databases (such as PostgreSQL) implement Row-Level Security (RLS). When RLS is active on a table, the database engine automatically appends tenant isolation filters (`WHERE merchant_id = current_setting(...)`) at the engine level, independent of the developer's application code. This eliminates the risk of human-error leaks. In FeelPay, RLS policies are applied across transaction tables, and combined with explicit Rust authorization middleware (`src/middleware/rbac.rs`) and connection-pooling state initializers, guaranteeing absolute logical data separation across all active merchant scopes.
Security in fintech also demands dynamic mitigation of cyber-attacks. Replay attacks—where an interceptor captures a valid API payload and resends it to trigger double-charges—are prevented using temporal nonces. Bignell (2022) describes a zero-trust network model where API calls must include a cryptographic signature, a unique random nonce, and a millisecond timestamp. The gateway verifies that the timestamp falls within a narrow window (e.g., 5 minutes) and uses a cache (Redis) to check if the nonce has been used. If the nonce exists, the request is immediately blocked, representing the highest standard of modern API interface protection.

4. Existing System Analysis
1. High Commission Friction and Platform Overhead: Standard payment aggregators in India (Razorpay, Cashfree, PayU) charge a flat fee between 2% and 3% on every single transaction, to which an additional 18% GST is added. For high-volume businesses, this commission friction represents a massive drain on profitability. Merchants have no ability to establish direct relationships with acquiring banks to reduce fee rates.
2. Strict RBI Aggregator Guidelines and Service Suspendability: Under current Reserve Bank of India (RBI) payment guidelines, third-party aggregators are subject to massive audit and capital reserves requirements. To comply, these aggregators employ automated KYC engines that freeze merchant accounts at the slightest administrative mismatch. When an account is frozen, the merchant's customer-facing checkout form is deactivated, and pending settlements are locked. Businesses can lose their primary digital cash flow for weeks without direct developer recourse or clear escalation paths.
3. Absence of Atomic Indian Tax Ledger Automation: Indian Income Tax rules mandate a 1% Tax Deducted at Source (TDS) deduction under Section 194O on e-commerce transaction settlements. Standard commercial gateways calculate basic totals and dump raw transaction details into asynchronous CSV exports. They do not record or deduct platform-fee GST (18%) and payout TDS (1%) atomically inside the database ledger during transaction success. Merchant accounting teams are forced to execute manual reconciliation steps every month, resulting in heavy accounting overhead and data mismatch risks.
4. Bot-Driven Card-Testing Fraud and Transaction Tampering: Monolithic legacy processors often run on traditional PHP or scripting frameworks with weak velocity enforcement middleware. Consequently, merchants frequently fall victim to card-testing attacks (where malicious actors use checkout scripts to test thousands of stolen card numbers in seconds). This results in massive chargeback dispute penalties, bank network fines, and merchant reputation destruction because the gateway failed to block the velocity surge in real time.
5. Noisy Neighbor Performance Degradation: Aggregator systems utilize massive shared database clusters to manage thousands of merchants. When a single major enterprise merchant experiences massive transaction volume (such as during a festival flash sale), the database connection pools of the shared cluster become saturated. This causes severe latency spikes and checkout timeouts for smaller merchants adjacent on the cluster, representing a classic multi-tenant noisy neighbor vulnerability.

6. Methodology / Planning of Work
6.1 High-Level Systems Architecture & Request Execution Pipeline
The FeelPay platform is architected as a highly modular, decoupled web service. The system separates the user interface (React 19 single page application) from the execution logic (Rust Actix Web microservice). This ensures that any concurrency spike on the client application does not saturate the transaction execution engine. The backend API gateway is designed as a pipeline containing specialized middleware filters that inspect every inbound connection before routing it to core business controllers, implementing a zero-trust network topology.
When an incoming HTTP request is received by the Actix Web server, it is sequentially processed by the following layers:
1. **Authentication Middleware**: Resolves caller context. If the request originates from the React dashboard, it validates the client's JWT session cookie. If the request is an API call from a developer's server, it extracts and hashes the `x-api-key` using PBKDF2, mapping it against active credentials.
2. **Temporal Nonce & Replay Prevention**: Checks the cryptographic header. Rejects calls where the client-timestamp deviates from the server clock by more than 300 seconds. If the timestamp is valid, it queries Redis to ensure the transaction nonce has not been used. If the nonce is unique, it is cached in Redis with a 5-minute TTL.
3. **Velocity Checker**: Uses Redis sliding-window counters to audit the request frequency. If an IP, card BIN prefix, or customer email domain exceeds the configured velocity rules, the request is immediately aborted with an HTTP 429 status.
4. **Logical Isolation Context**: Binds the authenticated `merchant_id` to the database query pool thread. This ensures that subsequent SQL queries run under Row-Level Security isolation.
Upon passing the security middleware layers, the request reaches the core modules: Transaction Processor, KYC Profile Manager, Settlement Engine, or the Webhook Dispatcher. For card transactions, raw PANs are immediately isolated and sent to the secure card vault. The vault encrypts card strings with AES-256-GCM and generates a unique token. The transaction processor routes this token to acquirer simulators or mock PSP nodes, writes transaction state changes to PostgreSQL, and releases a signed webhook event in the background, guaranteeing complete operational reliability and low network latency.

6.2 Relational Data Models & Atomic Double-Entry Financial Ledger
Data persistence and ledger integrity are the core focus of the FeelPay engine. To support complete merchant isolation in a shared database ecosystem, the PostgreSQL database is built with strict schema constraints. All tables—including `payment_orders`, `payment_attempts`, `api_keys`, `settlements`, `refunds`, and `audit_logs`—incorporate a `merchant_id` column as a primary foreign key. PostgreSQL Row-Level Security (RLS) is explicitly enabled on these tables. When an Actix Web database connection thread is acquired, it executes `SET LOCAL feelpay.current_merchant_id = ...`. The database automatically filters all queries based on this session state, blocking cross-merchant leakage at the core SQL layer.
To guarantee absolute financial accuracy, the ledger uses integer minor units (paise for INR) for all monetary fields, preventing the rounding discrepancies typical of IEEE 754 floating-point numbers. The financial ledger operates under double-entry bookkeeping rules, tracking funds across multiple balance states: available balance, pending balance, and payout reserve reserves. When a customer executes a payment of 10,000 paise (Rs. 100) and the transaction succeeds, the engine triggers an atomic SQL transaction:
- **Gross Credit**: Credits 10,000 paise to the merchant's pending balance.
- **Platform Fee split**: Calculates platform fee (e.g., 2% flat = 200 paise). Debits 200 paise from the merchant and credits it to the Platform Account.
- **GST deduction**: Computes 18% GST on the fee (18% of 200 paise = 36 paise). Debits 36 paise from the merchant and credits it to the Tax Account.
- **TDS tracking**: Under Section 194O, a 1% TDS deduction (1% of 10,000 paise = 100 paise) is recorded for fiscal reporting.
When payouts are compiled by the Settlement advanced service (`src/engine/services/settlement_advanced.rs`), the system calculates the net settlement amount: Gross Amount minus Platform Fee minus GST minus TDS. This net balance is transferred to the merchant's verified bank account (`bank_accounts` table), and the transaction is marked as `paid`. A UTR (Unique Transaction Reference) number is recorded, and the ledger accounts are updated to `captured` or `settled`. This design ensures that both the merchant and platform administrators can audit tax records in real time, making monthly GST and TDS filing seamless.

6.3 Project Planning & Phase Implementation (Phases 1 to 6)
The development and implementation of FeelPay are organized across twelve clear, sequential phases. This roadmap maps each phase to specific database migrations, Actix Web routers, and React frontend views, ensuring a highly structured development cycle.
Phase 1: Multi-Tenant Schema & Session Security (Weeks 1-2): Establish the database migration suite. Write initial SQL schemas for `merchants`, `users`, and `memberships` tables. Program JWT authentication routes in Rust (`src/api/auth.rs`) and secure cookie storage. Create React login, signup, and forgot-password components.
Phase 2: Tenant Isolation & RBAC Integration (Weeks 3-4): Develop SQL Row-Level Security rules. Code the backend context parser to extract `merchant_id` from parsed tokens and bind it to active threads. Enforce role authorizations (`owner`, `admin`, `developer`, `finance`, `support`, `read_only`) across all REST controllers. Integrate RBAC permissions in React navigation grids.
Phase 3: Multi-State KYC Wizard & Document Store (Weeks 5-6): Construct the multi-step React onboarding form. Program backend input validation rules (validating 10-digit PAN format, 15-digit GSTIN, bank IFSC numbers, and CIN structures). Configure local filesystem/S3 integration (`src/api/documents.rs`) for digital PDF uploads. Map verification steps (`draft`, `submitted`, `under_review`, `approved`, `restricted`, `rejected`).
Phase 4: Payment Processor & PCI Card Vault (Weeks 7-8): Build the transactional pipeline (`src/engine/pipeline.rs`). Code card credential vaulting using AES-256-GCM symmetric encryption. Program UPI VPA validations, deep-linking stubs, and netbanking acquiring simulations. Create payment checkout pages with dynamic loading widgets.
Phase 5: Webhook Dispatcher & State Logging (Weeks 9-10): Create transaction attempt event logging schemas. Write the background webhook manager in Rust. Compute request signatures using HMAC-SHA256 keys, append timestamp verification headers, and execute background webhook deliveries with automatic retries across increasing delays (5s, 15s, 60s, 300s).
Phase 6: Double-Entry Ledger & Standard Settlements (Weeks 11-12): Write PostgreSQL triggers to log double-entry transaction balances. Calculate platform transactional commissions (flat + percentage) per the active merchant `fee_plans`, deduct 18% GST, and credit net amounts to available merchant balances. Schedule standard T+2 settlement payouts.

Block velocity surges per customer IP, email domain, or card BIN prefix. Setup SendGrid SMTP integrations for email receipts, and Twilio/Exotel stubs for India-compliant SMS alerts. Write template compilers to dynamically substitute transaction variables (`{{customer_name}}`, `{{amount}}`).
Phase 12: Asynchronous Report Exports Panel (Weeks 23-24): Program the offline background reporting runner. Compile transaction ledger, settlement tax summaries, and GST fee calculations in the background using Tokio worker threads to prevent main thread blocking.
